Initial Setup for PostgreSQL 18.4

Build a verified local PostgreSQL cluster, create a limited application identity, and add network access only through explicit security and ownership gates.

1Overview / Goal

This decision-based tutorial covers a safe, local-first PostgreSQL initial setup: prove the intended version and target, create or identify one database cluster, start the intended server, validate a local connection, and create one least-privilege application role and database. The direct route is for a disposable Unix-like local environment; it is not a procedure for an unknown, shared, or production server.

Stop conditions. Do not continue with direct initialization if you do not own the data directory; the path is not empty; another team owns the service; the system is shared, production, or regulated; or required authorization/change approval is absent. PostgreSQL 18.4 was released May 14, 2026, but the PostgreSQL Version 18 documentation currently identifies 18.7. For a new installation, use the current approved 18.x patch unless an approved baseline specifically requires 18.4.
1
Target cluster

A known data directory, configuration, and server instance.

1
Local proof

A server status check and a successful local psql connection.

2
Scoped objects

An application role and an application database it owns.

Success criteria

  • The actual binary version, data directory, server/service owner, and configuration files are known.
  • The intended server is running and a local connection to postgres succeeds.
  • A non-superuser login role owns a dedicated application database and can connect to it locally.
  • Remote access remains unchanged unless there is a separate approved access, TLS, firewall, and rollback design.

2Required Information & Prerequisites

Gather these requirements before issuing a lifecycle, configuration, or object-creation command. This tutorial intentionally does not invent package-install commands or service names when the operating system and approved package are unknown.

Database cluster: an initialized PostgreSQL data directory with shared system catalogs, configuration, and one or more databases. In PostgreSQL administration, “cluster” does not necessarily mean multiple networked servers.

Version gate: 18.4 versus current 18.x
Decision requiredVerify locally

18.4 is a maintenance release and its release notes say a dump/restore is not required for an existing 18.x cluster. It is still a change requiring version, service, extension, backup, and application validation. Since the Version 18 documentation currently presents 18.7, obtain a decision whether “18.4” is an intentional pinned baseline or an outdated reference before initiating a new install.

4Step-by-Step Instructions

Step 1 — Establish the target and baseline

Action
Confirm the task is an authorized initial setup and record what you intend to operate.
Inputs
Approved binary/package record, target purpose, system owner, local/remote scope.
Exact instructions
Record the target host/workstation, expected data directory, intended port, intended bootstrap role, and whether access must remain local. Then run:
initdb --version
psql --version
Expected result
Both commands identify the intended 18.x toolset; if 18.4 is mandatory they should identify 18.4.
Verification
Confirm the tools come from the same approved installation and that no existing service is being confused with the target.
If unsuccessful
Stop. Do not mix binaries from different installations or proceed with unknown provenance.

Step 2A.1 — Prepare a direct local data directory (Path A)

Warning. Run only as the non-root account that will own this direct local server. Do not substitute a shared, package-managed, or production data directory. The test below stops rather than deleting existing files.
Action
Create a private, empty location for a new cluster.
Inputs
A controlled local path; the example uses a home-directory path.
Exact instructions
export PGDATA="$HOME/pgdata/18-local"
umask 077
mkdir -p "$PGDATA"
chmod 700 "$PGDATA"
test -z "$(find "$PGDATA" -mindepth 1 -maxdepth 1 -print -quit)" \
  && echo "Directory is empty" \
  || { echo "STOP: PGDATA is not empty: $PGDATA"; exit 1; }
Expected result
The final line reports that the directory is empty.
Verification
Run printf '%s\n' "$PGDATA" and inspect the printed path before continuing.
If unsuccessful
Do not empty the directory to force progress. Choose another approved empty path or switch to Path B.

Step 2A.2 — Initialize the direct local cluster (Path A)

Action
Create a new cluster and restrictive baseline local authentication rules.
Inputs
The validated PGDATA and PostgreSQL 18.x initdb.
Exact instructions
initdb -D "$PGDATA" \
  --auth-local=peer \
  --auth-host=scram-sha-256

Read the final summary. Do not use --no-sync for this baseline; PostgreSQL documents that it can leave a cluster corrupt after an operating-system crash.

Expected result
initdb creates cluster files, default configuration/HBA files, and the postgres, template1, and template0 databases.
Verification
test -f "$PGDATA/postgresql.conf" && \
test -f "$PGDATA/pg_hba.conf" && \
echo "cluster files present"
If unsuccessful
Read the exact error and check parent-directory permissions. Do not rerun as root.

Step 2A.3 — Start and check the direct local server (Path A)

Action
Start the new local server and prove that the same data directory is running.
Inputs
The initialized PGDATA.
Exact instructions
pg_ctl -D "$PGDATA" -l "$PGDATA/server.log" start
pg_ctl -D "$PGDATA" status
Expected result
Status reports a running server.
Verification
If unclear, read the final lines of $PGDATA/server.log; retain the full error if startup fails.
If unsuccessful
Do not start or stop a different instance. Use the log to isolate port conflict, permissions, or configuration failure; then see Troubleshooting.

Step 2B.1 — Use the approved package-managed route (Path B)

Tip. Package installations often initialize and start a cluster using distributor-specific paths/service controls. Use the approved package procedure rather than guessing a unit name, data directory, or bootstrap account.
Action
Identify service owner, data directory, endpoint, and authorized local connection route.
Inputs
Approved package record and service-administration procedure.
Exact instructions
Use the approved lifecycle method to identify whether the intended PostgreSQL service is running. With authorized database access, perform the read-only queries in Step 3. If the service is uninitialized, follow the package owner’s initialization instructions exactly.
Expected result
You can name the service owner, actual data directory, configuration/HBA path, and endpoint.
Verification
The Step 3 output matches the intended environment.
If unsuccessful
Pause. Do not initialize an unknown package path manually.

Step 2C.1 — Pass the shared/production gate (Path C)

Warning. This is a mandatory review gate, not a bypass. Initialization, authentication changes, restarts, or network exposure can affect other users and data.
Action
Establish an approved, reversible change before touching shared service/network controls.
Inputs
Approved change; named service owner; patch baseline; recovery evidence; maintenance window; required source/database/role; TLS/firewall plan.
Exact instructions
Document the service and data directory owner; define validation/rollback; use the approved configuration-management method; then have the authorized administrator perform the equivalent local verification in Step 3.
Expected result
A named owner, approved change record, rollback method, and narrow connection design exist.
Verification
Verify approval and recovery evidence through the designated organizational process.
If unsuccessful
Stop. This tutorial cannot authorize production operation or exposure.

Step 3 — Verify the intended local connection (all routes rejoin)

Action
Prove you reached the intended running cluster before creating objects or changing network access.
Inputs
Authorized bootstrap role. For direct Path A with local peer authentication, this is normally the OS account that ran initdb.
Exact instructions
psql -d postgres -v ON_ERROR_STOP=1 -c \
"SELECT current_database(), current_user, version();"
psql -d postgres -v ON_ERROR_STOP=1 -c \
"SHOW data_directory; SHOW config_file; SHOW hba_file; SHOW listen_addresses;"
Expected result
The first result identifies postgres, the expected bootstrap role, and the server version. The second identifies the actual instance paths/settings.
Verification
For Path A, data_directory equals $PGDATA.
If unsuccessful
Stop before role creation. Diagnose server status, wrong path, authentication, or wrong instance using Troubleshooting.

Step 4 — Create a scoped application role and database

Warning. This creates database objects. Execute only as an authorized bootstrap administrator on the verified cluster. Never put a real password in shell history, an SQL file, source code, or this tutorial.
Action
Create one non-superuser login role and one database owned by that role.
Inputs
Replace app_owner and app_db with approved, unused names.
Exact instructions
In an interactive psql -d postgres session, run:
CREATE ROLE app_owner
  LOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE
  NOREPLICATION NOBYPASSRLS;
CREATE DATABASE app_db OWNER app_owner;

Then set the password interactively, which avoids placing it in the SQL command line:

postgres=# \password app_owner
Enter new password: [approved managed secret]
Enter it again: [repeat secret]
postgres=# \q
Expected result
The role can log in but lacks superuser, database creation, role creation, replication, and row-security-bypass attributes; it owns app_db.
Verification
psql -d postgres -c "\du app_owner"
psql -d postgres -c "\l app_db"
If unsuccessful
If names already exist, do not alter or overwrite them blindly. Inspect ownership with the responsible administrator and choose approved names or stop.

Step 5 — Verify the application identity over local TCP

Action
Test loopback TCP; this exercises the local host rule without exposing the server externally.
Inputs
The role/database from Step 4 and its securely entered password.
Exact instructions
psql -h 127.0.0.1 -U app_owner -d app_db \
  -v ON_ERROR_STOP=1 \
  -c "SELECT current_user, current_database(), inet_client_addr();"
Expected result
The returned user is app_owner, database is app_db, and client address is local loopback.
Verification
This proves server, loopback listener, matching HBA rule, SCRAM password authentication, role, and database are aligned for this test.
If unsuccessful
Use Troubleshooting. Do not change authentication to broad trust merely to make the test pass.
Checkpoint — baseline complete. Record the data directory, configuration/HBA locations, port, role/database names, and tested connection string without a password. Continue only if remote access is a documented requirement.

Step 6 — Optional: add a narrowly scoped remote path (Path C only)

Warning. Do not apply this to a learning instance without approval. Remote access needs independent listener, HBA, firewall/routing, identity/secret, logging, and encryption controls. An HBA rule does not open a firewall port, prove TLS, or make a broad design safe.
Action
Allow one approved source to reach one database as one role using the approved authentication and TLS design.
Inputs
Approved client IP/CIDR, database, role, port, TLS/certificates, firewall policy, test client, rollback.
Exact instructions
First capture active values in Step 3. Use the authorized configuration-management process for approved listener/TLS changes. Then add a narrowly scoped illustrative template entry, replacing each placeholder:
# TYPE     DATABASE          USER              ADDRESS/CIDR             METHOD
hostssl    <APP_DATABASE>    <APP_LOGIN_ROLE>  <CLIENT_IP_OR_CIDR>      scram-sha-256
Reload through the approved service procedure or, where authorized, run SELECT pg_reload_conf();. Query pg_hba_file_rules for parsing errors before relying on the change. Test from the approved source with encryption and review logs.
Expected result
Only the specified source, user, and database use the intended remote path.
Verification
Confirm client source, encryption status, user, database, and firewall/log evidence; test that an unapproved source does not receive access.
If unsuccessful
Revert via the approved process. Stop/escalate if listener, TLS, or HBA behavior is not understood.
Why HBA order matters
Security-critical

PostgreSQL evaluates pg_hba.conf records in order and uses the first record that matches connection type, client source, requested database, and user. If authentication then fails, later records are not tried. Place narrow rules deliberately and validate parsed rules rather than relying on a broad later “fallback.”

Step 7 — Stop the direct local cluster when finished (Path A only)

Action
Cleanly stop the disposable direct local server when no longer needed.
Inputs
The same known PGDATA that created the direct cluster.
Exact instructions
pg_ctl -D "$PGDATA" stop -m fast
pg_ctl -D "$PGDATA" status
Expected result
Stop completes and status reports no server for that data directory.
Verification
The data directory remains intact for authorized later use; this does not delete the cluster.
If unsuccessful
Review the direct cluster log. Never use this direct lifecycle command against a shared/package-managed instance.

7Completion Checklist / Quick Reference

Do not declare success merely because a service appears to be running. Use the applicable acceptance checks below.

  • Target recorded: version, service/data-directory owner, actual data directory, configuration/HBA files, local endpoint, and lifecycle method are known.
  • Version decision made: 18.4 is an approved pinned baseline or a current approved 18.x patch is used.
  • Lifecycle verified: the intended server starts through the correct route and health/status is demonstrated.
  • Local bootstrap connection verified: psql -d postgres connects to the expected cluster and SHOW data_directory matches the recorded target.
  • Least-privilege identity verified: application role is not superuser/role/database admin, owns its application database, and can connect locally over TCP with a managed secret.
  • No unapproved exposure: network access is unchanged unless Path C approval, TLS/listener/firewall/HBA design, controlled test, and rollback are complete.
  • Operational record complete: record non-secret connection/configuration facts and change evidence per applicable policy.
