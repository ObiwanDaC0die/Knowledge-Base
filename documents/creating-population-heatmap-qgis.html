1Overview / Goal

Use this tutorial to create a heatmap that depicts the estimated spatial concentration of population, not a literal count at each pixel. The default route uses point features with a numeric population field and QGIS’s Heatmap (Kernel Density Estimation) processing tool.

Stop condition — do not continue yet: Pause if your data contain household-level, personally identifiable, sensitive facility, or otherwise restricted locations and you lack approval to display or aggregate them. Aggregate, mask, or obtain an approved public/authorized dataset before mapping. Also pause if you cannot identify the layer’s coordinate reference system (CRS), because a radius in degrees is not a meaningful distance.
Input
Point locations + population weight, or polygons to convert
Process
Kernel density estimation (KDE) into a raster
Output
Styled raster, saved project, documented parameters
Population heatmap / KDE: a raster surface created by spreading each input point’s influence over a selected search radius. Nearby influence is combined; optional weights let a larger population value contribute more than a smaller one.

Scope and success criteria

  • In scope: preparing data, selecting a route, generating a population-weighted or unweighted KDE raster, styling it, checking for misleading results, and saving reproducible settings.
  • Out of scope: estimating a statistically valid population surface from incomplete data, publishing sensitive locations, or treating KDE output as a census count without validation.
  • Success: the map has a documented projected CRS, an appropriate weight choice, a radius and pixel size expressed in usable linear units, an understandable legend, and a saved raster/project that another analyst can reproduce.

Start with Section 3 — Choose Your Path. The recommended default is Path A when you already have point features and a numeric population field. QGIS documentation describes the heatmap algorithm as creating a density raster from point features; its radius and output pixel size are in the layer’s map units. See the official references in Section 6.

Minimum CSV structure for a point-data route

A typical file has a header row and columns such as location_id,longitude,latitude,population. Do not select a CRS merely because it makes the points appear near your basemap.

4Step-by-Step Instructions

Step 1 — Define the map claim and create a safe working copy

Action: Write a one-sentence purpose, for example: “Show generalized population concentration from authorized 2025 settlement estimates within the study area.”

Inputs: source dataset, intended audience, permitted area of interest.

Exact instructions: Create a new QGIS project; save it in a clearly named working folder. Add the original layer without editing it. If transformations are needed, save outputs with new names such as population_points_projected.gpkg and population_kde_500m.tif.

Expected result: a saved project and an unmodified source layer.

Verification: In the Layers panel, identify the source layer and project filename; open the attribute table to confirm the expected records are present.

If unsuccessful: stop and correct access, file path, or data-source issues before making analysis outputs.

Warning — misleading precision: A heatmap is not evidence that every location within a bright area has the displayed population. It is a modeled surface based on input locations, weights, radius, and pixel size. Keep the map title, legend, and methods note consistent with that limitation.

Step 2 — Inspect geometry, population weights, and CRS

Action: determine the viable route and validate the key inputs.

Exact instructions: In QGIS, select the source layer. Check its geometry type and CRS in its layer information/properties. Open the attribute table; find the candidate population field; confirm it is numeric and investigate null, negative, or unexpectedly large values. Record the current CRS and units.

Expected result: you can answer: point or polygon; which field is population; whether the layer uses usable linear units.

Verification: Zoom to several known features. If coordinates or geometry appear far from the intended area, stop and resolve the CRS rather than changing it by guesswork.

Step 2A.1 — Path A: prepare a point layer in a suitable projected CRS

Action: use the existing point layer, or make a projected working copy.

Inputs: authorized point layer, numeric population field.

Exact instructions: If the layer’s CRS is geographic (typically degrees), run Reproject layer from Processing and choose a CRS appropriate to the study area with linear units. Save the output as a new file. If the existing CRS is already an appropriate projected CRS, retain it. Continue at Step 3.

Expected result: a point layer whose map units make the proposed KDE radius meaningful.

Verification: Inspect the output layer CRS and confirm the geometry overlays expected reference data.

If unsuccessful: do not proceed using degrees. Consult the data steward or GIS specialist for the authoritative CRS.

Step 2B.1 — Path B: create a documented point representation of polygon population

Action: make a point representation for each polygon only if it supports the map’s intended generalization.

Inputs: authorized polygon population layer, numeric population field, projected CRS.

Exact instructions: First create a projected working copy if required. Then run either Centroids or Point on surface from Processing. Prefer Point on surface where a centroid could fall outside an irregular polygon. Carry the population field into the result and save it as a new layer. Continue at Step 3.

Expected result: one representative point for each source polygon, with the population field retained.

Verification: Compare feature counts and population-field values between source polygons and output points.

If unsuccessful: revert to a choropleth or seek a gridded/disaggregated dataset. Do not imply within-polygon distribution you cannot support.

Step 2C.1 — Path C: stop or select a more defensible map

Action: do not create KDE output when the input does not support a spatial-concentration claim.

Exact instructions: Document the gap: missing locations, unknown CRS, unavailable permissions, or only a region-wide total. Request approved aggregate points/grids or use a map that matches the evidence, such as a regional total table or authorized polygon choropleth.

Terminal result: no heatmap is produced until a defensible location-based dataset and necessary approvals are available.

Step 3 — Choose initial KDE parameters

Action: select an initial radius, pixel size, and weighting choice that match the decision scale.

Exact instructions: Decide the smallest spatial pattern that should be visible to the audience. Set the radius larger than typical location uncertainty and smaller than the full study area. Set a pixel size substantially smaller than the radius so the surface is not blocky, while avoiding unnecessary file size. Select the numeric population field as the weight field if the purpose is population concentration; leave it unweighted only when every point intentionally represents one equal event.

Expected result: written initial values and a reason for each. Example only: a 1,000-metre radius with a 100-metre pixel size is a starting test for a city-scale analysis; it is not a universal setting.

Verification: Ask: “Can I explain this radius in plain language to the intended audience?” If not, revise it before processing.

Tip — parameter sensitivity: Create at least two trial surfaces with different plausible radii. If a conclusion changes materially, report the sensitivity or use a scale that is more defensible. Do not select a radius solely because it produces a dramatic pattern.

Step 4 — Run Heatmap (Kernel Density Estimation)

Action: generate a raster surface from the prepared point layer.

Inputs: projected point layer; selected radius and pixel size; optional population weight field; deliberate extent; output filename.

Exact instructions:

  1. Open Processing ▸ Toolbox and search for Heatmap (Kernel Density Estimation).
  2. Select the prepared point layer as the input.
  3. Enter the search radius in the layer’s linear map units.
  4. Set the output raster pixel size in the same units.
  5. Select the population field under the optional weight-field setting for a population-weighted result.
  6. Choose an output extent that covers the study area and enough surrounding area to inspect edge effects; avoid silently accepting an irrelevant project-wide extent.
  7. Save the output to a descriptive raster filename and run the algorithm.

Expected result: a new raster layer appears, with higher cell values where weighted point influence is concentrated.

Verification: Overlay the original points temporarily. Higher values should be plausibly associated with clusters and/or larger weights. Open raster layer properties and confirm the output CRS and extent.

If unsuccessful: record the exact Processing error. Check that the input is a point layer, the radius/pixel size are positive, the weight field is numeric, and the output location is writable. Return to Step 2 if the CRS or field is uncertain.

Step 5 — Style the raster without overstating the result

Action: use a sequential color ramp and a readable value range.

Exact instructions: Select the raster and open the Layer Styling panel. Use a single-band pseudocolor or another appropriate continuous-raster renderer. Select a perceptually ordered sequential ramp with light low values and darker high values. Set a transparent or very light treatment for zero/no-data only after confirming what those pixels mean. Add a legend label such as “Population-weighted KDE (relative intensity)” unless units and normalization have been separately validated.

Expected result: low-to-high values are visually ordered; bright/dark areas are distinguishable; the legend does not claim unverified people-per-area units.

Verification: Toggle the raster off/on and compare it with input points and boundaries. Ensure the styling does not hide large no-data areas or make an isolated high-weight point look like a broad region.

Step 6 — Check the result for analytical and visual errors

Action: test whether the surface is fit for the stated purpose.

Exact instructions: Review the map at the intended display scale. Check edge areas, water/uninhabitable areas, jurisdiction boundaries, and known clusters. Create a second plausible-radius output and compare the qualitative pattern. Add a source/method note listing dataset date, point representation, weight field, CRS, radius, pixel size, and any masking or exclusions.

Expected result: a documented result whose limitations are apparent.

Verification checkpoint: A reviewer can identify the input data, parameters, scale, and whether the map shows relative modeled intensity rather than exact population counts.

Step 7 — Save reproducible outputs

Action: preserve the QGIS project and analysis artifacts.

Exact instructions: Save the project. Retain the prepared point layer, heatmap raster, and a short methods note. For a shareable map, create a layout with title, legend, scale/context, data source, date, and limitations appropriate to the authorization and release rules that apply to the work.

Expected result: a colleague with authorized access can reproduce the map or inspect its settings.

Verification: Close and reopen the project (when operationally appropriate) and verify the paths resolve and the heatmap renders.

7Completion Checklist / Quick Reference

Declare the task complete only when the applicable route has reached a verifiable result and the following checks are satisfied.

  • Input authority and sensitivity: I used data I am authorized to analyze and display; any sensitive-location handling or aggregation requirement has been addressed.
  • CRS and scale: The input/output CRS is known, appropriate to the study area, and uses meaningful linear units for the selected radius and pixel size.
  • Population representation: I documented whether the heatmap was population-weighted; if polygons were converted to points, I documented the representation and its limitation.
  • Parameters: The radius, pixel size, kernel/other options, output extent, and weight field are recorded. I can explain why the parameters fit the intended scale.
  • Visual validation: I checked the raster against input points, boundaries, no-data areas, and at least one plausible alternative radius where the decision is consequential.
  • Map communication: Title, legend, source, date, and methods note accurately describe a modeled relative-density surface and do not imply unsupported exact counts.
  • Artifacts: The QGIS project, prepared point layer (if created), heatmap raster, and methods note are saved with understandable names; original input is preserved.
  • Route result: Path A produces a direct point-based KDE; Path B produces a documented point-representation KDE; Path C correctly produces no heatmap until deficiencies are resolved.
Final release check: Before sharing, use your organization’s access, handling, need-to-know, records, security, and release processes. This tutorial does not authorize uploading, publishing, or distributing a particular dataset or map.

Common next actions: create an approved print layout; compare results by time period using consistent parameters; summarize areas of relative concentration with boundaries; or select a different method (for example, a choropleth) if the available data are area-based rather than point-represented.
